# 按计划写代码和交付

确定项目后，开始前、每批改文件前都重读 `<project>/docs/xyf-easycode/PromptsRules.md`。
缺文件先读[模板](../xyf-easycode-install/PromptsRules.md)，说明缺项，交给 install 按授权补齐。读不到规则就暂停。

## 依据与交接

沿用确认的项目、架构、范围和授权。架构默认 `<project>/docs/xyf-easycode/html/software_architecture.js`。
读取 [check](../xyf-easycode-check/SKILL.md)生成或维护的 `<project>/docs/xyf-easycode/plans/<任务ID>.md`；缺计划、缺项或过期由 check 补齐。
ID 用本地时间 `yyyy_mm_dd_hh_mm_ss_ms`，24 小时制，毫秒 3 位；恢复沿用。
缺设计或要改架构，交给 [plan](../xyf-easycode-plan/SKILL.md)处理后结束本轮 code，等用户查看、修改并自行调用 check。
保留用户修改。网页部署交给 [install](../xyf-easycode-install/SKILL.md)。

主助手记录关联计划完整路径及 ID、开始时的版本和未提交修改；每轮检查版本另存，记录任务、负责人、可改文件、授权、进度、依据和下一步。
每批后、交接前更新。接着做先读 plan，再查文档、代码、依赖和未提交修改。

## 执行流程

步骤 2～4 按模块分批做。新的前置模块先通过 3、4。

### 1. 核对计划

核对现状、任务、顺序和验收；不重复规划。约定不清先查或问，暂停相关任务。说清方案和文件范围，用户单独回复“执行”才写；有效授权沿用，扩大范围重新确认。

### 2. 写代码和测试

子助手每次做一个模块，前置功能可用后再做。按约定的名称、类型、默认值和行为实现，复用代码，不写空壳或假结果。

逐个读取方法的 `interfaces[].flow` 和 `errors`。按流程顺序和条件，每步先加长注释，再写对应代码；按 `errors` 处理错误。
每个方法的步骤从 1 编号，注释文字用架构原文：

```text
/************************ 流程 1：步骤原文 ************************/
```

其他语言用支持的注释语法。事件流程也逐步写编号注释。流程缺失、含糊或与 plan 冲突时先查清或提问，不能猜。

按 plan 的“怎么测试”和架构要求运行测试，失败就修复重测，通过后停写交接。

### 3. 架构核对

主助手用 check 查本批及受影响代码，复核问题、依据、遗漏并更新计划。问题退回 2，查全通过才进 4。代码和架构状态不改。

### 4. 独立审查

未参与开发或修复的人用 [review-agent](../review-agent/SKILL.md)只读审查最终代码。有问题回 2，重新测试、核对再独立审查，全部解决才通过。

### 5. 整体验证

模块全通过、大家停写后，主助手按 review-agent 审查开始以来的所有改动及模块间调用。把功能连起来测试，再测旧功能，完成必要构建。修复后重跑相关测试、3 和 4，再复核整体。

### 6. 验收交付

主助手核对全部任务和依据。开发、测试、核对、审查全通过后，逐份核对项目、ID 和完成状态，仅删本次登记且全部完成的计划；其他计划和架构保留。表格列出改动、实际验证和结果。

## 分工与测试文件

子助手只写分配的模块和测试文件，回传结果；主助手更新 plan，检查和审查不改业务代码。
独立任务可并行，共享文件排队，每个模块或文件同时一人写。分工给出路径、模块 ID、范围、版本、授权和验收要求。架构、代码或依赖变了，重查受影响内容。

所有测试入口、用例、数据、临时文件、缓存、日志、覆盖率、报告、工作目录及相关构建、类型检查输出，都放在 `<project>/docs/xyf-easycode/tests/`。
并行测试分目录，业务源码和复用工具可从外部引用，不搬动或删除旧测试。

缺必要测试或独立审查就继续解决；助手不可用先协商。未通过不能报完成或删计划。提交、推送、合并或发布须用户明确要求。
