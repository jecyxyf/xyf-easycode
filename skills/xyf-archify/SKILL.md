# XYF-ARCHIFY

## 总目标

通过采访明确项目需求，整理功能清单，再结合现有架构提出分层、模块职责和接口方案。用户确认后生成 `software_architecture.js`，提供可继续编辑的架构网页。

已确认的架构配置是架构依据，新项目默认使用 `software_architecture.js`。本技能只讨论和维护架构，不阅读业务源码或判断代码实现；代码向架构看齐的工作由 [xyf-code](../xyf-code/SKILL.md) 负责。

## 执行流程

每步先完成工作，再用简短表格呈现结果，请用户确认。**收到明确确认后才能进入下一步；未回复、工具运行成功或已有文件都不等于确认。** 用户提出修改时，调整当前结果并重新确认；已明确确认且未变化的内容直接沿用。

项目目录 `<project>` 默认为当前目录，用户指定时再调整。写入前核对绝对路径，未经允许不超出项目目录。技能安装目录只作工具来源。用户只讨论或只生成配置时，省略部署。

### 1. 判断项目并准备工作区

**目标：** 明确项目位置、现有架构和网页是否需要初始化。

**步骤与约束：**

- 根据用户说明和现有架构判断新旧项目。已有项目先读当前架构配置，概括分层、模块、职责、接口和依赖；文件缺失时询问已有设计，不能据此认定为新项目，也不转去分析业务源码。
- 工作区默认 `<project>/docs/xyf-easycode/html/`，仅生成配置也沿用此位置；已有或用户指定路径在目录边界内继续使用，保留配置和网页定制。新配置采用 `globalThis.softwareArchitecture = <严格 JSON>;` 格式，通过 [ProjectFile.parse](../xyf-easycode-install/html/assert/project-file.js) 读取；已有 `.json` 用 `JSON.parse` 读取，不执行用户提供的配置文件。多个基准并存时先解决冲突。
- 需要网页且尚未初始化时，按 [xyf-easycode-install](../xyf-easycode-install/SKILL.md) 将 [html 目录](../xyf-easycode-install/html/) 的内容复制到工作区，并只在副本中处理语言和项目数据。网页直接打开 `<workspace>/index.html`，自动读取同目录的 `language.js` 和 `software_architecture.js`；无需 Node.js、构建或服务器。沿用已指定或现有的网页语言，新网页未指定时默认中文。
- 新项目用模型创建独立 ID 的空白配置，`repository.path` 初始化为项目目录的绝对路径。已有 JSON 若需要迁移给网页使用，先确认迁移后的配置路径和唯一架构依据，保留原文件与稳定 ID；不能用空模板覆盖已有设计。访问和保存方式见[网页说明](../xyf-easycode-install/html/README.md)。

**完成条件：** 用户确认项目位置、新旧项目判断及现有架构摘要；需要部署时，文件复制和语言设置完成，网页可直接打开并显示正确的配置，入口路径和保存方式已交付。

### 2. 采访项目需求

**目标：** 充分理解用户想解决什么问题、实现什么效果。

**步骤与约束：**

- 用大白话围绕使用场景、期望结果、本次范围和关键限制采访，一次只问一个关键问题；已知内容不重复问。有实际取舍时给简短选项和建议，不扩展无关功能，不盘问算法、库或存储实现。
- 全新项目才确认编程语言和部署平台；已有项目沿用架构约定，除非用户要求变更。
- 信息足以明确功能和架构范围时，就总结并请用户确认，不继续深挖实现细节，也不要求用户先想好模块或接口。

**完成条件：** 目标、场景、范围和限制已明确，用户确认理解准确。

### 3. 整理功能需求清单

**目标：** 将采访结果拆成明确、可核对的功能需求。

**步骤与约束：**

- 逐项说明要实现的功能、主要输入、预期结果和关键业务规则；区分本次新增、调整及保留的功能。
- 补问影响功能含义的缺口，不擅自增加业务规则，也不要求在终端逐字段细聊。

**完成条件：** 用户确认功能清单完整、范围正确，关键规则没有歧义。

### 4. 提出并确认架构方案

**目标：** 用合理的分层、模块和接口覆盖已确认的功能需求。

**步骤与约束：**

- 结合当前架构配置提出复用、新增或优化哪些模块；新项目给出初始架构。说明各层作用、模块职责与依赖，以及每个主要接口的用途、输入输出和关键行为。
- 按“分层 → 模块 → 接口”展示方案，并列出每项功能由哪些模块和接口承担，检查遗漏、职责重叠及接口冲突。
- 逐个与用户确认受影响模块及接口。能从已确认内容确定的配置细节自行整理，影响业务含义或对外行为的选择交给用户。

**完成条件：** 用户确认模块职责、主要接口和需求覆盖关系；没有影响架构方案的关键疑问。

### 5. 保存架构配置

**目标：** 将确认方案保存成有效配置，交给用户继续核对。

**步骤与约束：**

- 仅将已确认方案写入正式配置。写前重读当前内容，处理版本冲突和已知未保存修改，保留稳定 ID、无关内容和布局；依照[数据指南](../xyf-easycode-install/html/references/architecture-data.jsonc)及[模型](../xyf-easycode-install/html/assert/model.js)完整记录需求、分层、模块、依赖和接口，不编造源码证据。新增布局按层从上到下，模块不重叠，连线清晰。
- 通过 `Model.validate` 检查数据；新 JS 配置用 [ProjectFile.stringify](../xyf-easycode-install/html/assert/project-file.js) 序列化，保留的旧 JSON 继续使用严格 JSON。写入前核对文件仍与读取版本一致，保存后回读、解析并比较。不得执行用户配置中的代码。只读校验不加载网页应用或调用补默认值的函数。
- 交付网页时，直接打开 `index.html` 检查语言、数据加载和编辑界面，确认使用约定的配置。浏览器直接写回文件需要用户选择原文件并授权；不支持时下载 JS 副本，由用户替换后刷新。只要求配置时不增加网页部署与检查。

**完成条件：** 配置校验和保存回读通过，用户确认交付结果。交付配置路径、网页入口路径（如有）及检查结果；未完成或未验证的事项明确列出，不自动开始编程。
