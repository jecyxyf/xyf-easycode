# 读架构、问需求、定方案、写计划

确定项目后，运行前及每批写入前重读 `<project>/docs/xyf-easycode/PromptsRules.md`；未部署先读[模板](../xyf-easycode-install/PromptsRules.md)，补齐交给 install 按授权处理。

## 1. 读取当前状态

沿用已确认的项目架构文件，默认 `<project>/docs/xyf-easycode/html/software_architecture.js`。从架构数据读取现有分层、模块、接口、数据和状态；本阶段只了解现状。
先确认读的是目标项目文件，不能把安装模板或自行举的例子当成项目事实。缺文件先找正确路径，不能假装读完。
成功读完后，只回复这四个字：**读取完毕**。

## 2. 明确需求

问清用户要什么、具体做什么、使用流程、范围和限制。一次问一个关键问题；已知信息沿用，能自行查清的先查。需求没问清就继续沟通，不让用户代替你设计模块或接口。
问清后，逐行填写真实答案，固定用下面的表头：

| 需求 | 做什么 |
| --- | --- |

## 3. 确定方案

根据已确认需求，说明哪个模块的哪个接口需要实现什么，以及怎么验收。优先复用已有能力，按需查成熟做法；把用途、收什么数据、返回什么结果、数据类型和默认值、先后关系、出错怎么办写清楚，确保每条需求都有办法，并写明怎样检查、什么结果算通过。
逐条对照第 2 步的需求，在“需要实现什么”中标明对应需求。每条需求都要有具体的模块、接口、实现办法和验收要求。有遗漏就继续补齐，全部覆盖后才能进入第 4 步。
只填写本项目的方案，固定用下面的表头：

| 模块 | 接口 | 需要实现什么 | 怎么验收 |
| --- | --- | --- | --- |

## 4. 更新架构，生成新 plan

方案和写入范围说清楚，用户针对该方案单独回复“执行”后，才更新架构数据并生成 plan。
写前重读原文件，处理别人刚改过或尚未保存的内容。保留原有 ID、无关设计和布局；新内容用不重复的 ID。新设计标为 `planned`（准备实现）；已验证内容的实际含义改了，标为 `modified`（需要重新核对）。

JS 文件用 [ProjectFile.parse](../xyf-easycode-install/html/assert/project-file.js) 读取 JSON 数据，不运行配置代码，用 `ProjectFile.stringify` 写回；JSON 文件用 `JSON.parse`，保持原路径和格式。写入前后用 [Model.validate](../xyf-easycode-install/html/assert/model.js) 检查，再重新打开文件，对照需求、接口和相互关系，确认没写错。字段见[数据说明](../xyf-easycode-install/html/references/architecture-data.jsonc)。

plan 保存到 `<project>/docs/xyf-easycode/plans/<任务ID>.md`。任务 ID 用本地时间 `yyyy_mm_dd_hh_mm_ss_ms`，24 小时制，毫秒 3 位；重名重新取时间，恢复沿用原 ID。
plan 记录项目、架构及关联计划的完整路径、初始基准（含未提交修改）、需求、授权、负责人、进度、依据和下一步；逐项写清任务、模块和接口 ID、实现要求、修改文件、依赖与执行顺序、验收要求。每批工作后及交接前更新；恢复先读计划再核实现状。其他任务保留，本任务计划由 code 验收后清理。

交付时给出架构文件和新 plan 的完整路径，并用下面的表头列出执行计划：

| 顺序 | 模块 | 接口 | 要实现什么 | 修改文件 | 怎么验收 |
| --- | --- | --- | --- | --- | --- |

本次规划的疑问、冲突和遗漏必须查清并解决；确实需要用户决定的及时问，等待时继续其他能做的工作。需求没清楚、方案没定、授权没取得或检查没通过，就没有完成；继续处理，不能把问题留给 code。
全部解决、架构和计划核对通过后才交付。后续由 [code](../xyf-easycode-code/SKILL.md) 按 plan 编码，本技能到此结束。
