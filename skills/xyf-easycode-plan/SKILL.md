# 读架构、问需求、定方案、改架构

`<project>` 是目标项目的目录。

确定项目后，开始前、每批改文件前，都重读 `<project>/docs/xyf-easycode/PromptsRules.md`。
缺文件先读[规则模板](../xyf-easycode-install/PromptsRules.md)，由 install 按规则取得同意后补齐。

## 1. 读取当前状态

读取已确认的项目架构文件，默认 `<project>/docs/xyf-easycode/html/software_architecture.js`。
从数据读出各层、模块、接口、数据和状态。这里只了解现在的情况。
确认文件属于目标项目，不能拿模板或自编例子当事实。找不到文件就先找正确路径。
确实读完后，只回复：**读取完毕**。

## 2. 明确需求

问清用户要什么、做什么、怎么用，这次做哪些、不做哪些、有什么限制。一次只问一个关键问题。
已知的不再问，能自己查清的先查。没问清就继续问，模块和接口由助手设计。
问清后，把真实答案填入表格：

| 需求 | 做什么 |
| --- | --- |

## 3. 确定方案

模块是一组相关功能；接口是调用功能的入口。先看已有功能能否用，再按需查成熟做法。
每个接口写清：用途、收到和返回的数据、数据类型（如文字、数字）、没填时用什么值、先后关系、出错怎么办。
逐条对照第 2 步，在“需要实现什么”中写明对应需求。每条都要有模块、接口、做法和验收要求。少一条就补齐，全部对应上才能进入第 4 步。
只填本项目的方案。“怎么验收”写清怎样检查、什么结果算通过：

| 模块 | 接口 | 需要实现什么 | 怎么验收 |
| --- | --- | --- | --- |

## 4. 更新架构 JSON 数据

说清方案、要改哪些文件和哪些内容。用户针对方案单独回复“执行”，才能更新架构 JSON 数据。
改前重读原文件，核对别人新改或尚未保存的内容，避免丢失。
按下面的数据说明，把第 3 步确认的方案写进架构数据。
保留原有编号 ID、无关设计和布局；新 ID 不能重复。
新设计标为 `planned`（准备实现）。原来检查通过的设计改了，标为 `modified`（需要重新检查）。

JS 用 [ProjectFile.parse](../xyf-easycode-install/html/assert/project-file.js) 读数据，不运行文件里的代码；用 `ProjectFile.stringify` 保存。
JSON 用 `JSON.parse` 读取。保留原路径和格式。
改前、改后都用 [Model.validate](../xyf-easycode-install/html/assert/model.js) 检查。保存后重新读取，核对需求、接口及它们的关系。字段见[数据说明](../xyf-easycode-install/html/references/architecture-data.jsonc)。

### 交付

先解决本次规划的疑问、冲突和遗漏。需要用户决定的及时问，等回复时继续做其他能做的事。
需求不清、方案未定、没获同意或检查没过，都要继续处理，不能当成完成。
全部解决、架构核对通过后，给出架构文件的完整路径，按下面表格汇报：

| 架构文件 | 修改内容 | 检查结果 |
| --- | --- | --- |

交给用户查看和修改，本技能到此结束。不生成 plan，也不自动调用 check 或 code。
用户查看、按需修改后，自行调用 [check](../xyf-easycode-check/SKILL.md)。
