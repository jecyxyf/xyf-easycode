# 需求沟通与软件架构设计

## 架构依据

沿用已确认的目标项目和架构路径，默认 `<project>/docs/xyf-easycode/html/software_architecture.js`。缺少文档时从代码识别现状；空项目从需求开始。多个版本先确定依据，不把工具模板当成项目事实。

JS 配置用 [ProjectFile.parse](../xyf-easycode-install/html/assert/project-file.js) 从文本解析，不执行配置代码；旧 JSON 用 `JSON.parse`。字段见[数据说明](../xyf-easycode-install/html/references/architecture-data.jsonc)。

## 计划文档

独立任务以本地时间 `yyyy_mm_dd_hh_mm_ss_ms` 为 ID（24 小时制，毫秒固定 3 位），保存为 `<project>/docs/xyf-easycode/plans/<任务ID>.md`。重名重新取时间，恢复沿用 ID。
主代理开始建档，记录项目、架构及关联计划完整路径、初始基准（含未提交修改）、需求与候选方案；逐项写明任务、文件范围、改法、依赖顺序、验收要求、授权、负责人、进度、证据和下一步。待确认项标明且不执行。每轮沟通有进展、每批工作及交接前更新；恢复先读再核实内容。保留其他任务，编码验收后清理本任务文档。

## 执行流程

| 阶段 | 要求 |
| --- | --- |
| 1. 了解现状 | 阅读架构资料、项目结构和关键代码，识别职责、依赖及限制，区分已实现、计划中和未知内容。先概览整体，再深入相关部分；用“名称、作用”两列按分层、模块、必要接口缩进展示。 |
| 2. 采访需求 | 按下述采访方式，明确目标、使用场景、核心流程、功能范围、关键限制和验收要求。不让客户代替架构师设计模块或接口。 |
| 3. 提出方案 | 优先复用已有能力，按需检索成熟方案并核实适用性。有实际取舍时比较可行方案的收益、成本及影响，给出推荐和依据，不凑选项。按“需求、解决办法、预期结果”展示。 |
| 4. 设计框架 | 将需求落实到模块、职责、依赖、接口、数据和验收要求，核对覆盖、冲突及可行性。说明功能变化、删除或改名、兼容影响及写入范围。简单改动一次确认完整方案和写入范围，复杂改动分阶段；沿用仍有效的确认。 |
| 5. 生成或更新 | 只写已确认内容。写前重读文件，解决并发修改或未保存内容；保留稳定 ID、无关设计和布局，新内容用唯一 ID。新设计标为 `planned`；已验证内容实质修改后改为 `modified`，同步检查受影响项。 |

## 头脑风暴式采访

- 先开放提问，让客户描述实际困难和期待；再用场景、例子或少量选项启发，允许自由回答。
- 用大白话，一次只问一个影响方案的关键问题。已知信息直接沿用，先自行查证能查明的事实。
- 客户提出做法时，理解背后的目标；主动指出遗漏、矛盾和更简单可靠的办法，解释取舍。
- 区分已确认需求、候选想法和待定问题，候选想法不能直接成为需求。
- 目标、流程、范围、关键限制及验收要求清楚后，简短复述理解，进入方案设计；关键问题未解决时暂停受影响部分，不无限采访。

## 文件核对与交付

写入前后用 [Model.validate](../xyf-easycode-install/html/assert/model.js) 校验。校验通过后，JS 用 `ProjectFile.stringify` 保存，旧 JSON 保持原格式；回读比较需求、接口、依赖及改动范围。本次引入的问题必须修正复查；原有问题报告并按授权处理。

交付供 [code](../xyf-easycode-code/SKILL.md) 执行的计划，简表列路径、架构改动、检查结果及未决事项。格式通过不代表功能实现或运行验收通过。完成即结束，不自动编码、部署网页或启动其他流程。
