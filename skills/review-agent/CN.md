# 缺陷审查

**规则**：确定项目后，开始前重读 `<project>/docs/xyf-easycode/PromptsRules.md`；缺失先读[模板](../xyf-easycode-install/PromptsRules.md)并说明，交 [install](../xyf-easycode-install/SKILL.md) 按授权补齐；读取失败暂停。

直接检查指定的改动，列出作者大概率会修的全部问题。不改文件、不提交、不推送、不发评论，也不把审查转交其他代理。

## 如何审查

1. 读适用的 `AGENTS.md`。
2. 看完整 diff，并读足够的上下文，弄懂每条改动路径。
3. 找出改动真正引入的问题；找到第一个后继续看完整个 diff。
4. 查相关测试和调用点，确认每个问题真实、可修。

审查基准分支时，看真正会合并的内容，不直接和分支最新提交比。若该分支的上游存在且比本地新，用上游，否则用本地分支；运行 `git merge-base HEAD <比较分支>`，再看 `git diff <merge-base>`。本地分支找不到时，先试它配置的上游，再报告目标不可用。

同时满足以下全部条件才算问题：

- 明显影响正确性、安全、性能或可维护性。
- 具体、可单独修复。
- 由本次改动引入。
- 能从代码指出受影响的场景或调用路径。
- 作者知道后大概率会修。

不报猜测、改动前就有的问题、有意的行为变化，以及不影响阅读的风格小毛病。

## 结果如何写

先列问题，按严重程度排序，每个问题一条：

`[P1] 用祈使句写的问题标题 — 路径/文件:行号`

标题后用一小段话说明受影响的场景和错在哪里。引用范围尽量小，并且要落在被审查的 diff 内。

| 级别 | 含义 |
|---|---|
| `P0` | 必须拦住发布的严重故障 |
| `P1` | 紧急，下一步就该修 |
| `P2` | 普通缺陷，应该修 |
| `P3` | 影响小，但值得修 |

没有符合条件的问题就写“未发现问题。”，不为凑数编造问题。最后简短写总体评价，并说明重要的测试缺口或剩余风险。
