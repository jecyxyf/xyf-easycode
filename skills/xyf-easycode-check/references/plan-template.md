# plan 模板

根据实际检查结果写修改任务，让 code 可以直接照着改和测试。下面的占位内容都要换成真实答案，不编项目事实。

## plan 正文

# 修改任务：<任务ID>

项目：<项目完整路径>
架构：<架构文件完整路径>
关联计划：<完整路径；没有则写“无”>
开始前的情况：<本轮核对的架构、源码、配置版本及未提交修改>
写入授权：<用户已同意的文件和内容；没有则写“未授权”>

| 顺序 | 模块 | 接口 | 需要改什么 | 怎么改 | 怎么测试 |
| --- | --- | --- | --- | --- | --- |
| <执行顺序> | <真实名称和 ID> | <真实名称和 ID> | <检查发现的问题、依据和要达到的结果> | <问题原因、文件路径、位置和具体改法> | <测试文件、步骤或命令、输入数据、什么结果算通过> |

检查覆盖及证据：<检查过哪些内容，各项负责人、依据的文件路径和行号>
任务进度：<按表中顺序记录负责人、授权、进度、实际验证依据和下一步>

## 填写要求

- 每行是一项具体任务，按先后顺序排列；要等别的任务完成，就在“怎么改”中写明对应顺序号。
- 模块和接口写真实名称及架构 ID。整个模块的问题写“模块整体”，列全受影响的接口，不硬编接口。
- “需要改什么”写出代码哪里不符合已确认的架构、依据在哪里、改完应是什么样。缺少的功能也要写成任务。
- “怎么改”写清具体改法。已有代码写文件路径、行号和代码位置；新文件写完整路径和新增内容。只写“修复问题”不算写清楚。
- “怎么测试”写能照着做的步骤或命令、输入及预期结果，覆盖相关的正常、边界和出错情况。需要新增测试时，文件放在 `<project>/docs/xyf-easycode/tests/`。
- check 只写测试办法，不运行测试。实际验证依据没有就写“未运行”，不能写成通过。生成 plan 不代表已获得编码授权。
- 方案有疑问先查清；需要用户决定时及时问。未查清的内容标明未完成，不能让 code 猜怎么做。
- 查全且无差异时，保留表头、不编任务，写“未发现不符合项，无需修复”。没查完就写未完成，继续处理。
- 每批及交接前更新进度，保留已有任务记录。check 被 code 调用时更新指定计划。
