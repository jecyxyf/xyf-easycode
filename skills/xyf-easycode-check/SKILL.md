# 检查代码，写修改任务

`<project>` 是目标项目目录。开始前、每批改文件前，都重读 `<project>/docs/xyf-easycode/PromptsRules.md`。
缺文件先读[规则模板](../xyf-easycode-install/PromptsRules.md)，说明缺项，由 install 取得写入同意后补齐。读不到规则就暂停。

## 1. 确认检查范围

沿用已确认的项目、架构和范围；没限定就查全部。架构默认 `<project>/docs/xyf-easycode/html/software_architecture.js`。
找准程序入口和文件，确认检查哪一版。模板不能当需求；跳过无关依赖、缓存和生成文件。

JS 用 [ProjectFile.parse](../xyf-easycode-install/html/assert/project-file.js) 读取，JSON 用 `JSON.parse`，用 [Model.validate](../xyf-easycode-install/html/assert/model.js) 检查。不运行配置代码，不擅自补值。
其他文档逐条对照。字段见[数据说明](../xyf-easycode-install/html/references/architecture-data.jsonc)。

代码、架构和状态只看不改，不运行程序或测试。只有主助手写 plan。

## 2. 逐个检查模块

| 检查什么 | 怎么检查 |
| --- | --- |
| 模块 | 用途、代码名、语言、文件位置、所在层是否符合要求。 |
| 功能 | 正常、达到或超出限制时的结果，以及带来的其他变化是否正确；不能只有空壳或假结果。 |
| 使用别的功能 | 导入、注册、调用是否正确，运行前需要的东西是否齐全。 |
| 参数 | 名称、类型（如文字、数字）、用途、必填项、不填时的值是否一致。 |
| 数据 | 结构、字段名、类型、含义是否与实际数据一致。 |
| 接口 | 方法是否存在、能否调用；用途、输入和返回结果是否符合要求。 |
| 流程和出错 | 步骤、遇到不同情况怎么做、出错怎么办及错误传给谁是否正确。 |
| 消息 | 名称、方向、参数、流程、谁发送谁接收是否一致。 |
| 测试 | 步骤、检查内容、预期结果是否齐全；测试及生成文件放在 `<project>/docs/xyf-easycode/tests/`。 |
| 依据 | 文件路径、行号、代码名、状态是否与实际一致。 |

方法在 `interfaces` 中。输入输出为空要查约定；默认值没写或为空，不能当成零或空串。
`relations` 只标注画布关系；状态不能证明代码已完成。按明确要求判断；布局、颜色只查设置是否合法。

## 3. 查清问题

| 步骤 | 怎么做 |
| --- | --- |
| 列清单 | 架构读取一次，记录架构、代码、配置版本及未提交修改。按模块和成员 ID 列全检查项，用 `rg` 找位置再读文件。 |
| 分工 | 按模块或相关功能分给多个助手，给出路径、版本、要求、检查项和授权。每项一人，共用功能一人查，使用方仍查调用。小任务或助手不可用时逐个查。 |
| 找依据 | 沿入口、注册、调用和数据传递查，记录查了什么、依据和问题。疑点继续查；缺权限或需用户决定就问，等待时查其他项。 |
| 主助手复查 | 核对问题、模块间调用，补查矛盾和遗漏；确认文件版本，改动及受影响的地方重查。 |

第一次查全。记录完整，且要求、代码、依赖、配置和范围都没变，才可沿用；变了就重查它和用到它的地方。

## 4. 写 plan 并交付

任务 ID 用本地时间 `yyyy_mm_dd_hh_mm_ss_ms`，24 小时制，毫秒 3 位。保存到 `<project>/docs/xyf-easycode/plans/<任务ID>.md`。
重名重新取时间；继续或复查沿用 ID。code 调用时更新指定计划。

主助手按 [plan 模板](references/plan-template.md)写任务，依据检查结果写清模块、接口、改什么、怎么改、怎么测试。
没确认的事项标明，不执行。每批做完、交接前更新；接着做先读 plan 再查现状。保留其他进度，code 验收后清理本任务计划。

交付 plan 完整路径和摘要，供 [code](../xyf-easycode-code/SKILL.md)执行。同一原因的问题合并，列全受影响成员。
查全且无差异写“未发现不符合项，无需修复”；没查完写未完成，继续处理。
已获同意的架构调整交给 [plan](../xyf-easycode-plan/SKILL.md)，本技能不自动修复。
