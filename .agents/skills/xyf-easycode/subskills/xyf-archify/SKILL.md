# XYF 架构

完成两件事：把已确认需求或实际源码整理为 `archify.json`，并提供读写同一配置的架构网页。按以下五步推进，沿用已完成的工作和已有确认；用户只要求讨论、处理数据或梳理源码时，遵守其范围，不强行增加其他工作。

架构工作由当前 Agent 完成。需求采访在本技能内进行，不再转交独立的 brainstorming 流程。业务代码的实现、修复和测试交给 [xyf-code](../xyf-code/SKILL.md)；不自动创建独立规格、计划文件或提交 Git。

## 1. 初始化工作区

**目标：已有工作区则复用，没有则创建可以访问的空白架构网页。**

- 先明确实际项目、工作区和授权。新工作区使用 `<project>/docs/archify/`；用户指定的路径或已有的旧版 `docs/archfiy/` 工作区继续沿用，不自动迁移。多个配置来源冲突时先确认基准。是否需要初始化，与项目是否已有业务代码无关。
- 首次创建网页且语言尚未指定时，先问“架构网页使用什么语言？”。接受任意自然语言，已有明确答案直接沿用。已有网页保留其语言；网页语言与编程语言分别处理。
- 将技能安装根目录的 `tools/` 完整复制到工作区的 `tools/`。只在副本不存在时新建；已有副本、配置、网页定制和未保存修改不能直接覆盖。
- 调用 [xyf-web-language](../xyf-web-language/SKILL.md)，明确传入网页语言和工作区工具副本的绝对路径，限定只翻译该副本。保留英文名称、代码标识和样式，不修改技能安装目录的共享模板。
- 没有业务配置时，通过模型创建带独立项目 ID 的空白配置供网页初始化；已有配置则保留并加载。空白配置只表示工作区已就绪，不表示需求或架构已完成。工具副本中的 `archify.json` 只是模板，不能作为当前项目的数据基准。
- 使用翻译后的工具生成网页并启动本地服务。需要 Node.js 22+；缺失或版本过低时，安装前取得同意。核验并复用同一工作区的已有服务；新增服务使用可用的五位数端口，记录实际地址和重启命令。
- 部署工具必须支持下面的目录关系，并将服务绑定到工作区根目录的配置。工具不支持时报告具体阻碍，不得改用工具内的模板数据启动服务，也不得将未启动的网页说成可访问。

| 工作区内位置 | 用途 |
| --- | --- |
| `archify.json` | 唯一的当前项目配置 |
| `index.html` | 加载当前配置的网页入口 |
| `tools/` | 项目独立的工具和翻译副本 |
| `html/` | 由工具部署的运行文件 |
| `ReadMe.md` | 实际访问地址、端口和重启命令 |

**完成条件：网页可访问，读取的是当前工作区配置，项目数据与工具模板已明确区分。**

## 2. 了解当前框架

**目标：弄清现有软件已经具备什么，以及本次工作影响哪里。**

- 读取实际的 `archify.json`，了解项目用途、模块职责、接口和依赖；必要时查看相关源码。新初始化的空白配置不代表项目没有代码。
- 先限定分析范围，再搜索或深入阅读。优先使用用户指定的业务源码；否则根据顶层构建、启动配置定位。排除技能目录、辅助工具、第三方实现、生成网页、构建产物和缓存，除非用户明确将它们作为分析对象。
- 根据入口、注册关系、调用和数据流核实实际行为，不能只凭文件名、注释或配置中的路径下结论。外部依赖只记录项目可见的调用约定，不猜测其内部实现。
- 分清已实现功能、已确认但尚未实现的设计和不确定事项。配置与源码不一致时记录差异，不自动用一方覆盖另一方；不得把改进建议写成已有事实。
- 用简短表格概括相关模块、职责、现状和本次影响。确实没有现有架构或代码时说明情况，按全新项目继续。

**完成条件：已有能力、相关模块、证据来源和未明确事项已梳理清楚，足以开展本次需求讨论或源码整理。**

## 3. 采访并明确功能需求

**目标：把用户想做的事情拆成具体、可确认的功能需求，先不急着拆模块。**

- 从提示词、前文和现有资料整理已知信息，简短复述本次目标与范围，主动提出功能草案，让用户补充和纠正。
- 全新项目确认要实现的功能、编程语言和部署平台。已有项目沿用现有技术与部署方式，只讨论本次新增或调整的需求；用户明确提出的技术迁移属于本次变更。
- 一次只问一个会影响功能或架构的关键问题。存在实际取舍时给出简短选项、建议和理由；简单事项自行判断，已确认内容不重复询问。
- 围绕当前目标逐步收敛，不主动扩展无关功能，也不要求用户替 Agent 完成技术设计。分清用户明确提出的要求、Agent 的建议和仍待确认的内容。
- 用功能清单说明每项功能要完成什么、主要输入和结果，以及影响结果的重要规则。业务含义不明确时追问，不擅自补充业务规则。
- 仅梳理现有源码时，以代码事实整理功能清单，只询问影响范围或结论的缺口，不强迫用户提出新需求。

**完成条件：本次功能范围和关键业务规则已明确；需求设计获得有效确认，源码梳理具有对应证据。**

## 4. 拆分并确认模块方案

**目标：让功能需求都有模块承担，逐个明确模块职责和对外接口。**

- 根据功能清单提出合理可实现的模块搭配方案，明确复用、新增或优化哪些模块。优先利用已有能力，不机械地把一个文件当成一个模块，也不预先限定模块数量。
- 说明每个模块负责什么、覆盖哪些功能、依赖哪些模块，以及彼此如何配合。检查职责重叠、功能遗漏和接口冲突，不凭画布箭头猜测依赖。
- 逐个确认模块的主要对外接口：接口用途、主要输入输出、关键行为及必要的错误处理。终端沟通以能判断功能是否满足为准，不逐字段盘问；能从源码、既有约定或已确认需求确定的配置细节由 Agent 整理。
- 会改变业务含义或对外行为的缺口必须确认，不能以“技术细节”为由自行决定。用简短表格记录模块方案和待定项，已有确认只在受影响时重新讨论。
- 纯源码梳理以实际模块和接口为依据；保留真实代码标识，不把理想方案混入现状。改进建议单独提出，用户同意后才作为设计变更处理。

**完成条件：范围内的功能均有对应模块，职责和主要接口清楚，没有影响实现的关键疑问；方案已确认或有充分源码证据。**

## 5. 生成最终 archify.json

**目标：将确认结果转为完整、有效的配置，让用户在网页上继续查看和调整。**

- 写入前重新读取当前配置，核对版本并处理已知的网页未保存修改。以实际工作区的 JSON 为基准，不能用工具模板或旧 HTML 快照覆盖当前数据。按稳定 ID 定位对象，保留无关字段、布局和用户修改。
- 以 [model.js](../../tools/html/assets/model.js) 和[数据指南](../../tools/html/templates/archifytemplate.template.jsonc) 为模型依据。新对象使用模型构造函数，语义修改使用相应更新函数；ID 全局唯一，改名保持 ID，删除时清理引用。
- 按模型完整记录范围内的模块、需求、依赖和相关对外成员，包括参数、结构、方法、事件及测试要求。不得只抽取代表性接口。名称、类型、默认值、流程和错误处理应来自已确认需求或实际源码；不适用的内容才能留空，不能用示例值掩盖缺口。
- 设计内容使用 `planned`；有实际来源证据的内容使用 `verified`；已有内容发生语义变化时按模型标记并重新核验。来源记录实际读过的路径和位置，版本信息包含当前工作区差异；不编造源码证据或 Git 信息。`verified` 不代表业务测试通过。
- 正式方法的输入输出必须完整明确，确认标记与事实一致。未解决事项不能通过空数组、默认值或 `unknowns: []` 隐藏；存在关键缺口时先补齐，不能宣称最终配置已完成。
- 按职责和依赖安排分层、模块及连线，分层从上到下，保持内容和箭头清晰。保留范围外布局；连线必须符合已确认关系或实际调用、导入、事件和读写证据。
- 使用 [ProjectFile](../../tools/html/assets/project-file.js) 和[文件读写工具](../../tools/html/scripts/files.mjs) 解析、保存配置。采用严格 JSON、两个空格缩进和末尾换行；通过 `expectedVersion` 检查外部修改，写入后回读并深度比较。处理模型校验错误和相关警告，不为通过校验编造内容。
- 保存后确认网页和服务读写工作区根目录的同一个 `archify.json`。只更新配置时不重新覆盖工具或网页；修改工具后才重新生成受影响的入口。另存副本和 HTML 快照不代表当前配置已保存。

按实际工作区路径执行数据与服务检查：

```sh
node "<workspace>/tools/html/scripts/check.mjs" "<workspace>/archify.json"
node "<workspace>/tools/html/scripts/check.mjs" "<workspace>/index.html"
node "<workspace>/tools/html/scripts/check.mjs" --url "<实际 HTTP 地址>"
```

打开实际网页检查加载、模块、接口、布局和箭头；保存、刷新、重启及冲突行为在隔离测试项目验证，不将测试数据写入正式架构。API 检查不能代替浏览器检查，架构检查不能代替业务代码测试。

**完成条件：配置符合已确认需求或源码事实，模型校验与保存回读通过，网页加载同一配置。** 用简短表格交付配置路径、网页地址、处理范围、实际检查结果和未完成事项；如有阻碍或未执行的验证，如实说明。
