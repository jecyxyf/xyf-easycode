## 1. 目标

- 做一套系统，实时显示“要做的”和“已经做好的”，就像军队打仗一样。
- AI 一边工作，一边汇报完成情况。
- 用户从系统里实时了解当前进度，并且能随时提出新的要求。
- 不像 dsh 那样让 AI 一路做到底（太绝对）。人和 AI 在中间要能交流，对最终执行达成一致。

## 4. 从 dsh 借鉴什么

### 4.1 用饭店来理解 dsh

| 饭店里的事 | dsh 里叫什么 | 它在做什么 |
| --- | --- | --- |
| 服务员听客人说话 | 来源 | 盯着 GitHub 和飞书，有人说话就记下来 |
| 先看是不是真的在点菜 | 准入、评估 | 只听名单上的人；闲聊不算，真要做事才算 |
| 写一张点菜单 | 工单 | 一件事一张单 |
| 单子上写明“只做这道菜” | 授权范围 | 范围写死，想多做就得另开一张单 |
| 店长只把单子交给厨师 | 主 AI | 只派活，不炒菜，也不改菜单 |
| 厨师自己做菜、自己尝 | 干活的 AI | 每个厨师有自己的灶台，自己写代码、自己测试 |
| 客人中途说“少放辣” | 跟进消息 | 这句话直接传给正在做这道菜的厨师 |
| 厨师拿不准就去问客人 | 请示 | 一次只问一个问题，其他菜照常做 |
| 客人说“先别做” | 暂停 | 一直停着，客人说“可以了”才继续 |
| 菜做好，端到点菜的那桌 | 回原处汇报 | 在哪儿提的需求，就在哪儿回复结果 |
| 墙上的屏幕显示哪桌在等 | 面板 | 先显示需要人处理的事，正常的不占地方 |
| 停电后重新开店 | 重启恢复 | 先看每道菜做到哪了，再接着做，不重复做 |

| 一张图看进度 | |
| 做完逐条验收 | |
| 断了能接着做 | |

### 4.3 授权范围

授权范围就是点菜单上那一行：**只做这道菜**。它正好解决 EasyCode 的初衷：AI 越做越多、收不住。

| 规矩 | 意思 |
| --- | --- |
| 写上去就不能改 | AI 不能自己觉得“顺手多改点更好”就去改 |
| 想多做就另开一张单 | 每多做一样，都要用户点头 |
| 做完了单子还在 | 小的后续跟进，还按这张单做 |
| 只有用户能作废 | AI 不能自己说算了 |
| 规矩变了要再核对 | 重新开工前，先确认按现在的规矩还能不能做 |

我们的工单上要写清楚：做什么（对应的模块和接口）、改哪些文件、不做什么、谁在什么时候同意的。

## 5. 四个技能

| 技能 | 一句话 | 负责 |
| --- | --- | --- |
| 安装 | 把进度图摆好 | 装技能、网页、进度图文件和公共规则；已有的数据和改动都保留 |
| 工单 | 和用户谈 | 聊需求、改架构；把进度图上的差异变成任务；向用户提问并附推荐答案；记录同意；处理随时下的新指令；最后逐条验收，写交付清单和 PR 说明 |
| 代码 | 去干活 | 只做用户同意过的任务；边做边上报；每一步之前查收件箱；做完先自查，再查错 |
| 进度图 | 和代码对 | 对照代码看进度：哪些做完了、哪些还缺、哪些和架构不一样；用户要求时，按实际代码修正进度图 |

分工：**工单对人，代码对活，进度图对代码。**

```text
安装 → 工单（谈需求、画地形、派任务）→ 代码（干活、上报）→ 进度图（查进度）→ 工单（验收、交付）
                 ↑ 用户随时下新指令                                ↓ 用户要求时，修正进度图
```

现有 7 个技能的去向：

| 现在的技能 | 并到哪 |
| --- | --- |
| install | 安装 |
| xyf-easycode（总入口） | 删掉 |
| requirements | 工单 |
| check | 进度图 |
| sync | 进度图 |
| code | 代码 |
| review-agent | 代码 |

### 6.2 网页上能做什么

| 功能 | 说明 |
| --- | --- |
| 进度面板 | 工单分 4 组：等你处理、进行中、排队中、已结束；每张单显示对应的模块和 AI 最新的汇报 |

### 6.3 AI 用的命令（`progress.py`）

| 命令 | 做什么 |
| --- | --- |
| `status` | 看全部工单和它们的状态 |
| `inbox` | 看用户新下的指令和操作，看完记为已读 |
| `new` / `edit` | 写工单草稿 / 修改草稿 |
| `report` | 上报进度 |
| `ask` | 提问，附推荐答案 |
| `ack` | 回执“收到” |

### 6.4 记录怎么存

所有记录写进 `docs/xyf-easycode/html/progress.jsonl`，一行一条，**只往后加，从不改旧的**，所以用户和 AI 同时写也不会互相覆盖。

| 谁 | 能写哪些记录 |
| --- | --- |
| AI | 新建工单草稿、修改草稿、回执“收到”、上报进度（进行中、就绪、受阻、失败、无需处理）、提问（附推荐答案） |
| 用户 | 同意、不做（写原因）、暂停、继续、批注、回答问题、下新指令、验收 |

### 6.5 工单现在在等谁

照着 dsh 的 `src/core/stage.ts` 做：从上往下看，第一条对上的就是当前状态。

| 顺序 | 条件 | 显示 |
| --- | --- | --- |
| 1 | 已验收、不做或无需处理 | 已结束 |
| 2 | 用户暂停了 | 暂停中 |
| 3 | AI 的问题用户还没回答 | 等你回答 |
| 4 | AI 报告“就绪” | 等你验收 |
| 5 | AI 报告“受阻”或“失败” | 等你处理 |
| 6 | 还是草稿 | 等你同意 |
| 7 | 已同意，AI 正在做 | 进行中 |
| 8 | 已同意，还没开始 | 排队中 |

### 6.6 程序会拦住的事

| 拦住什么 | 为什么 |
| --- | --- |
| AI 不能替用户点同意、验收、继续 | 这些只有用户能做 |
| 没同意或暂停中的工单，AI 不能上报“进行中” | 没下单不能开火 |
| 已同意的工单，AI 不能再改范围 | 想多做就得另开一张单 |

这一层是防止 AI 手滑，不是严格的安全防线：AI 硬要直接改文件，程序也拦不住。dsh 也是这么写的。

### 6.7 已知的取舍

现在的 sync 是**系统层面**禁止 AI 自动调用的。并进进度图以后，进度图本身必须能被 AI 调用，所以“只有用户要求时才修进度图”只能写成文字规则。
